- 2026-10-23 — **A container cached on `globalThis` leaks classes across Next's server layers** (step 28). Pages and route handlers evaluate `@devmentor/core` in separate module graphs; whichever built the `globalThis` container first supplied every service, so after `/sign-in` rendered, `UserService` in a route threw the *page graph's* `UnauthorizedError` and the route graph's `apiHandler` (`instanceof AppError`) logged it as a 500 — only in the built app, never in unit tests, where there is one graph. Fix: cache the container per module graph (`getContainer` in `container.ts`, `resetContainer` for tests) and keep only the ORM pool on `globalThis` (entities are already `globalThis` singletons). Symptom to recognise: pino `err.type` is a minified one-letter name and the message is a typed error's. An integration scenario that renders a page *before* calling a route through an error path is what catches it.
- 2026-10-23 — **Email/password registration keeps a pre-account-hijack risk** (step 27). Claiming an unverified row writes the registrant's hash at once, so an attacker can register a victim's address with their own password; if the victim then clicks the verification mail, the row is verified *with the attacker's password*. Mitigation chosen: every verification link is bound to an HMAC fingerprint (keyed from the `SESSION_SECRET` family, 128 bits, never the hash itself) of the row's current `password_hash`, so any later registration invalidates every earlier link and only the newest registrant's link verifies; the mail tells anyone who did not sign up not to open the link and to ignore the email. Open follow-up: set (or confirm) the password at verification time instead of at registration, which closes the hole.
- 2026-10-23 — Two facts from the rate limiter (B8, step 23). (1) **Next's server fills `x-forwarded-for` from the socket only when the header is absent** (`req.headers['x-forwarded-for'] ??= socket.remoteAddress` in `next/dist/server/base-server.js`), so without a proxy a client-sent value survives untouched: `TRUSTED_PROXY_HOPS=0` must trust no entry, and N hops means the Nth entry from the right. (2) **MikroORM v7's `em.execute(sql, params)` inlines `?` params into the SQL text** (`prepareQuery` → `CompiledQuery.raw`), not a bound-parameter call — pass ISO strings with an explicit `?::timestamptz` cast, and prove raw SQL against a Testcontainers database (`tests/integration/rate-limit.integration.test.ts`), since a mocked `execute` cannot catch a statement error.

- 2026-10-23 — Three traps from the password service (B9, step 22). (1) **scrypt N=2¹⁷/r=8 needs *more* than 128·N·r = 128 MiB of `maxmem`**: Node's 32 MiB default and exactly 128 MiB both throw `ERR_CRYPTO_INVALID_SCRYPT_PARAMS` synchronously, so `SCRYPT_MAXMEM` is 256 MiB. (2) **`promisify(scrypt)`'s typings drop the options overload**; cast it once (`scryptAsync` in `password.service.ts`) rather than hand-wrapping the callback, whose `error ?` branch is unreachable for coverage (invalid params throw before the callback). (3) **There is no Prettier config**, so a bare `npx prettier --write` reformats to double quotes / 80 columns; match the house style with `--single-quote --print-width 100`. The seeder's constants are importable from core as `@devmentor/db/seeders`.
- 2026-10-23 — Two traps from `auth-password` (step 21). (1) **`migration:create` and `migration:up` write different snapshots**: create serialises the entity's `CHECK` text, up re-introspects the database (`(cardinality(roles) > 0) AND …`). The committed `.snapshot-devmentor.json` holds the introspected form, so take the `devmentor.json` that `migration:up` writes — copying create's output churns the check for no schema change. (2) **`passwordHash` is `.hidden()`, deliberately not `.lazy()`**: hidden keeps it out of `toObject()`/`JSON.stringify`, while lazy would leave it `undefined` on a plain `findOne`, so the seeder's `existing.passwordHash ??= …` would overwrite a real hash. `db` cannot import core's password service, so the seeder stores a precomputed `scrypt$N=131072,r=8,p=1$<b64 salt16>$<b64 key64>` and its test re-derives it with `scryptSync`, pinning the format step 22 must verify.
- 2026-10-23 — **Vitest treats a function returned from `beforeEach` as that test's teardown**, so `beforeEach(() => vi.mocked(fn).mockReset())` (concise arrow) returns the mock and Vitest *calls it* after each test — with a `mockRejectedValue` set, that call throws the sentinel and fails a passing test. Always write `beforeEach(() => { vi.mocked(fn).mockReset(); })`. Also from step 19: the layout guard lines stay byte-identical; the shell reads the name and roles through a separate `requirePageUser` call in `components/shell/signed-in-shell.tsx`.

- 2026-10-23 — Three traps from the E01 pages (step 16). (1) **The mock identity adapter redirects to `${APP_URL}/api/auth/github/callback`, and `APP_URL` defaults to `http://localhost:3000`**, so on the harness's random port every mock sign-in would leave the app (and the OAuth state cookie, set on `127.0.0.1`, would not travel). `integrationChildEnvironment(databaseUrl, appUrl)` now sets `APP_URL`; `global-setup.ts` reserves the port before building. (2) **Next route-group folders need escaping in `coverage.include`**: `(auth)` is glob syntax, so write `packages/app/src/app/\\(auth\\)/…` or the file is silently not measured. (3) A `page.tsx` may export only Next's page fields, so page-local helpers (sign-in copy, `returnTo` href) live in a colocated `.ts` module with its own coverage entry.
- 2026-10-23 — Two traps from F3/F4 (page guards, `WorkflowAction`). (1) **In flat ESLint config, a later entry for `no-restricted-imports` matching the same files replaces the earlier one instead of merging**, so the third-party patterns (`next`/`react`) had to join each package's existing workspace list in one `boundary(files, workspaces, frameworks)` call — a separate `next` entry for `packages/core/**` would have silently dropped the `@devmentor/*` rules. (2) **jsdom's `window.location` is unforgeable** (`vi.spyOn(window.location, 'assign')` and `defineProperty` fail); under Vitest's jsdom environment `vi.stubGlobal('location', { ...window.location, assign })` is what `window.location.assign` resolves to, and `vi.unstubAllGlobals()` restores it. `@next/next/no-location-assign-relative-destination` warns on the deliberate hard navigation in `SignOutButton`; it is disabled on that line with the reason.
- 2026-10-23 — **The OAuth state can't be signed exactly as the spec's diagram shows (`subject: safeReturnTo(?returnTo, '')`)**: `TokenService.signPurposeToken` refuses an empty subject, so every sign-in without `returnTo` would throw. `createOauthState` (`services/auth/oauth-state.ts`) signs `<random nonce>.<returnTo>` instead. The nonce also makes each attempt's state unique. `verifyOauthState` splits at the first `.`, and the callback still re-sanitises the result. Two more traps: (1) only the `Headers.append` path can put two `Set-Cookie`s on a redirect (`redirectResponse` in `http/cookies.ts`), and (2) running `next dev` rewrites `packages/app/next-env.d.ts` to `.next/dev/types`, so revert it before committing.

- 2026-10-23 — **A unique-violation race in Postgres cannot be recovered inside the same transaction**: the failed `INSERT` aborts it, so `UserService.findOrCreateFromGithub` re-runs its whole `em.transactional` once (the winner has committed by then, so the lookup matches) and emits events only after commit. Catch `UniqueConstraintViolationException` (re-exported from `@devmentor/db`) and check `.constraint` — the pg error's own properties are copied onto it — against the expected constraint names; rethrow everything else. To *prove* the race deterministically, hold `lock table users in access exclusive mode` on a third connection, `vi.waitFor` until `pg_stat_activity` shows both callers `wait_event_type = 'Lock'`, then commit the lock (`tests/integration/user-github-race.integration.test.ts`).
- 2026-10-23 — **`vi.useFakeTimers()` does not drive `AbortSignal.timeout`**, so a test that advances fake time to expire `fetchJson`'s 10 s budget just hangs until Vitest's 5 s test timeout. When a caller (e.g. `GithubIdentityAdapter`) does not expose `timeoutMs`, spy instead: `const real = AbortSignal.timeout.bind(AbortSignal); vi.spyOn(AbortSignal, 'timeout').mockImplementation(() => real(5))`, then assert the spy saw `10_000` — real timeout path, real `TimeoutError`, and the default budget stays asserted.

- 2026-10-23 — **awilix hands a scoped `asFunction` factory the resolving scope's own `cradle` proxy, and `scope.cradle` is identity-stable**, so a `WeakMap` keyed on the cradle can record per-scope facts (here: which session cookie a request scope's lazy `session` key was built from) without adding a `Cradle` key. `requireSession(req, cradle)` uses it to reuse the scope's memoised `Promise<Session | null>` — one `findOne(User)` per scope — and falls back to its own live check for any other cradle. Async resolution is modelled as a memoised promise because awilix resolution is synchronous. Two test traps hit on the way: a destructuring default (`{ secret = SECRET } = {}`) silently replaces an explicit `undefined`, and v8 can report a missed branch for `cond ? await a : await b` — write `await (cond ? a : b)`.
- 2026-10-23 — MikroORM v7 `text[]` with `p` builders: `p.array<UserRole>()` maps a Postgres `text[]` to a typed array and round-trips (quotes, commas, `$contains`); `.default(['mentee'])` emits `default '{mentee}'`. Prefer it plus an entity-level `checks: [...]` over `p.enum(ROLES).array()`, whose auto-generated `<@` check accepts `'{}'`. Two migration traps: (1) `migrations.snapshotName: 'devmentor'` makes local `migration:create`/`migration:up` write `migrations/devmentor.json`, while the committed snapshot is `.snapshot-devmentor.json` (the harness forces it via `MIKRO_ORM_MIGRATIONS_SNAPSHOT_NAME`) — copy the new content over `.snapshot-devmentor.json` and delete `devmentor.json`; (2) the root `db:migrate` nests a second `npm run`, so `npm run db:migrate -- --to X` silently drops `--to` and migrates to latest — call `npm run migration:up --workspace @devmentor/db -- --to X`.
- 2026-09-10 — **Storybook and esbuild treat any ancestor `.pnp.cjs` as Yarn Plug'n'Play configuration, even inside a nested npm project.** The symptom is valid Storybook imports failing with “The Yarn Plug'n'Play manifest forbids importing” after `npm ci`, while CI passes on a machine without the unrelated manifest. DevMentor's launcher runs the installed Storybook CLI from an isolated OS-temporary cache directory and supplies the real `.storybook` directory absolutely; do not delete or rewrite a developer's parent Yarn workspace to fix the npm project.
- 2026-09-08 — Three traps found while specifying E02 (`.ai/specs/2026-09-08-mentors-become-bookable.md`) that bite anyone touching roles, slots, or a MikroORM relation before its table exists. (1) **`grantRole` bumps `session_version`, so granting a role signs the caller out unless the route re-issues the cookie.** E01 puts `grantRole` on the closed list of `session_version` triggers; invitation acceptance (#15) is the first grant path, and a handler that commits the transaction without signing a fresh cookie leaves the user's own action invalidating their token — the redirect to `/mentor` then lands on sign-in. Only a route handler can set a cookie in the App Router, so this can never be fixed in a page or a service. (2) **A slot is a bare start instant but the *mentee* picks 25 or 50 minutes at booking (#17 + #21), so slots at 14:00 and 14:30 can double-book a mentor** — neither issue notices. The read-time filter is `viableLengths(slotStart, occupied, lengths)`; the guarantee is *not* a per-slot lock, which two concurrent bookings on two different slots sail straight through. Serialise on the **mentor** row (`SELECT … FOR UPDATE` on `mentor_profiles`) and back it with `EXCLUDE USING gist (mentor_profile_id WITH =, tstzrange(starts_at, ends_at) WITH &&)` on `bookings`. (3) **Never declare a MikroORM relation whose column does not exist yet.** A `Slot.booking` property with no `booking_id` column puts the column in every generated `SELECT` (so all reads of `slots` fail) and regenerates it on the next `db:migration:create` diff against the committed snapshot. Also note two boundaries that block the obvious implementation: `packages/db/**` may not import `@devmentor/core` (`eslint.config.mjs:44-48`), so a migration cannot call a vocabulary's `sqlValueList()` or a `uniqueSlug()` helper — hand-write the SQL and guard the drift with a `core`-side test that reads the migration file; and `SDLC.md:97` grades **any** schema migration `risk-high`, however small the feature.

- 2026-09-08 — **A "required in production" env check must not live in the zod schema.** `npm run build` forces `NODE_ENV=production`, the CI Build job sets no env at all, and `getEnv()` is reachable at build time from `admin/page.tsx` and the pino logger — so a schema refine that fails on a *missing* `SESSION_SECRET` in production would break every CI build. Put such checks at first container creation (`createContainer`), which only ever runs at request time. Schema-level refines are fine for *dangerous* combinations that are only ever set deliberately (e.g. `AUTH_IDENTITY_ADAPTER=mock` without `INTEGRATION_TEST_RUN=1`). Recorded in primitives spec B6.
- 2026-09-06 — **`npm run db:up` does not work in this sandbox — there is no Docker and no `psql`.** Neither `docker`, `docker compose`, nor any PostgreSQL client/server binary is on `PATH`, and there is no passwordless `sudo` to install one, so `docker-compose.yml` is unusable here. What *is* available is the sandbox's own PostgreSQL 17 on `127.0.0.1:5432` reachable as superuser `postgres`/`postgres` (the same server the injected `DATABASE_URL` points at, database `open-mercato`). To provision a fresh checkout: run `npm install` first (it brings in `pg` as a MikroORM transitive dep), then drive SQL through `node -e "const {Client}=require('pg') ..."` — `CREATE ROLE devmentor LOGIN PASSWORD 'devmentor' CREATEDB` and `CREATE DATABASE devmentor OWNER devmentor` — so the repo's documented `devmentor`/`devmentor` defaults still hold and `.env` stays consistent with `.env.example` and CI. Then `DATABASE_URL=postgres://devmentor:devmentor@127.0.0.1:5432/devmentor npm run db:migrate && ... npm run db:seed` (the explicit prefix is still required — see the 2026-09-04 entry below). Verify against `select current_database()`, not the CLI's `injected env` line, which lies.
- 2026-09-04 — Four constraints found while specifying E01 (`.ai/specs/2026-09-04-accounts-and-roles.md`) that will bite anyone adding UI, a scoped list, or admin chrome. (1) **There is no React test toolchain.** `vitest.config.mts` sets `environment: 'node'` and there is no `jsdom`, `@testing-library/react`, or `@vitejs/plugin-react` anywhere; no `*.test.tsx` exists. Any story adding `.tsx` must install and configure them first, or it cannot meet `AGENTS.md`'s 100%-per-file bar. Server components are testable by invoking the async function and asserting the returned element tree — no DOM needed; only client components need jsdom. (2) **`makeCrudRoute` cannot see the session.** `resolve` is `(cradle: Cradle) => CrudService` and `authorize` is `(req, cradle) => void | Promise<void>` — neither hands a `Session` to the service, so a per-caller-scoped list (`listForMentee`/`listForMentor`) cannot ride `makeCrudRoute` without changing `MakeCrudRouteOptions`/`CrudService`, both protected §2 exports. Also note `authorize: async (req) => requireRole(...)` does **not** typecheck (`requireRole` returns `Session`, not `void`) — use a braced body. (3) **The admin chrome is asserted behaviour, not free.** `tests/integration/admin.integration.test.ts:22` asserts `link "Users"`, which `BACKWARD_COMPATIBILITY.md` §7 names; replacing `admin/layout.tsx`'s sidebar must preserve an accessible `link "Users"` or update the test in the same PR. (4) `packages/db/src/entities/base.entity.ts` claims a "uuid v7 primary key (time-sortable)" but uses `crypto.randomUUID()`, which is **v4** — the comment is wrong, the ids are not sortable.
- 2026-09-04 — An OAuth **state** cookie must be `SameSite=Lax`, never `Strict`. The engineering-standards spec suggests "`lax` (or `strict` for auth-only routes)", and `Strict` looks like the safer read for an auth cookie — but the provider's callback is a cross-site top-level navigation, so a `Strict` cookie is not sent and *every* sign-in fails state validation. Related: `Response.redirect()` cannot carry `Set-Cookie`; build `new Response(null, { status: 302, headers })` when a redirect must also set the session cookie.

- 2026-09-04 — Sandbox `next dev` serving 500s on every route usually means the pm2 `workspace-preview` process is **stale**, not that the app is broken. It is launched once via `openmercato.toml` → `scripts/preview.sh`; a process started before the DevMentor repo replaced the `sandbox-next-seed` scaffold keeps running `next dev` with cwd `/workspace`, where there is no `app/` dir, so Turbopack panics with `ENOENT: scandir '/workspace/app'` and every request 500s. Check `~/.pm2/logs/workspace-preview-error.log`, then `npx pm2 restart workspace-preview`.
- 2026-09-04 — This sandbox force-injects `DATABASE_URL=postgres://postgres:postgres@127.0.0.1:5432/open-mercato` (see `CEZ_ENV_PASSTHROUGH`, which re-injects it into spawned processes, so a plain `unset` in a launcher script does not stick), and `createOrmConfig()` prefers `DATABASE_URL` over the discrete `DB_*` vars. Neither dotenv (`mikro-orm.config.ts` uses plain `loadEnv({ path })`) nor Next overrides a variable already in `process.env`, so the ambient URL silently wins and both the app and every `npm run db:*` command target the wrong database. The CLI still prints `injected env (11) from ../../.env`, which looks like `.env` won; it didn't. Remedies: `.env` now sets `DATABASE_URL` explicitly, `scripts/preview.sh` re-exports `.env` over the inherited environment for the dev server, and one-off CLI runs should be prefixed with `DATABASE_URL=postgres://devmentor:devmentor@127.0.0.1:5432/devmentor` and confirmed with `migration:list`. Do **not** "fix" this with `loadEnv({ override: true })` in `mikro-orm.config.ts`: `tests/integration/environment.ts` passes ephemeral Testcontainers config to child processes through the parent environment, and overriding would break it.
- 2026-09-03 — **`vi.resetModules()` + `await import()` per test is a timeout trap for anything importing `@mikro-orm/*`.** `packages/db/src/config.test.ts` reset the module registry in every case to defeat `getDbEnv`'s module-scope cache, so each test re-imported the entire ORM graph from cold *inside* the test body and blew the 5s default timeout on a loaded machine (2/4 cases failed under CPU contention; the file took 25s). Fix: stub the dependency instead of resetting the registry — `vi.mock('./env', () => ({ getDbEnv: () => current }))` plus one dynamic `import('./config')` at module scope, where no test timeout applies. Per-test time went 25s → 9ms. Reset the registry only when you are genuinely testing module-initialization behavior, and reproduce suspected flakes under `for i in $(seq 8); do (while :; do :; done) & done` rather than trusting a green single run.
- 2026-09-03 — **`.env.example` documents two mutually exclusive connection styles**, so "is this `.env` complete?" cannot be a raw key-set comparison. `DATABASE_URL` is commented out in the example while `DB_HOST`/`DB_PORT`/`DB_NAME`/`DB_USER`/`DB_PASSWORD` are live assignments, so `npm run setup` warned that a perfectly good URL-style `.env` was missing five variables — the exact setup the README's "Bring your own PostgreSQL" section tells people to use. Fix: `DATABASE_URL_SUPERSEDES` in `scripts/setup/steps.mjs`, letting a configured URL satisfy the discrete parts it replaces while pool sizing and `DB_DEBUG` stay required. Any new "is it configured?" check has to encode the same precedence the two zod schemas use.
- 2026-09-03 — MikroORM's **seeder glob defaults to `!(*.d).{js,ts}`**, so it imports *every* TS file in `seeder.path` to build its class map. Adding the repo-mandated colocated `database.seeder.test.ts` therefore broke `npm run db:seed` with `TypeError: Cannot read properties of undefined (reading 'config')` — the CLI was importing a Vitest file outside the Vitest runner. Fix: set `seeder.glob: '!(*.d|*.test).{js,ts}'` in `packages/db/src/config.ts`. Watch for the same trap if `migrations` ever gets colocated tests (its default glob is `!(*.d).{js,ts,cjs}`).
- 2026-09-03 — A `spawn()`-based helper must decide whether "command not found" is an *exception* or *data*. In `scripts/setup`, rejecting on the child's `error` event made the installer crash with an ENOENT stack on machines without Docker, bypassing the preflight message written for exactly that case. Missing-optional-tool is a normal outcome: resolve with a sentinel non-zero exit code instead of rejecting.
- 2026-09-02 — In a shared `makeCrudRoute`, don't assume Next always passes `ctx.params`. A **collection** route (`/api/users/route.ts`, non-dynamic) is invoked with no params, so `await ctx.params` is `undefined` and `params[idParam]` throws `Cannot read properties of undefined (reading 'id')`. Guard: `const params = ctx?.params ? await ctx.params : undefined`.
- 2026-09-02 — Services return **DTOs (plain objects), not ORM entities**, across the API boundary. `JSON.stringify` of a MikroORM entity with a bidirectional relation (User 1:1 MentorProfile) risks a cycle; a `toDto()` mapper in the service keeps the envelope clean and gives the route a stable shape. See `.ai/specs/2026-09-01-engineering-standards.md` (SRP).
- 2026-09-02 — The API envelope is a **shape convention, not a shared type**: `@devmentor/core/http` (`ApiResponseBody`) and `@devmentor/ui/backend/api` (`ApiResult`) declare it independently because `ui` must not import `core`. `ui` gained a `zod` dependency so `CrudForm` can take the same schema the server validates with (DRY without importing core).
- 2026-09-01 — MikroORM v7 + Next monorepo gotchas, see [details](lessons/2026-09-01-mikro-orm-v7-next-monorepo.md): (1) v7 has no core decorators — use `defineEntity` + `p` builders; (2) cross-entity relations need per-property thunks (`() => p.oneToOne(X)...`) because `oneToOne` already wraps its arg as `entity: () => target`; (3) register entities as `globalThis` singletons or Next's RSC/SSR/route graphs create duplicate schema instances and `populate` throws `Cannot read properties of undefined (reading 'filter')`; (4) `MikroORM.init()` no longer connects — call `orm.connect()` and don't cache the failed promise; (5) `em.persistAndFlush` removed — use `persist` + `flush`.
- 2026-09-01 — Turbopack does not rewrite `.js`→`.ts` in relative imports the way `tsc` does; use **extensionless** relative imports in TS-source workspace packages (works for tsc/Turbopack/tsx). Symptom was `Module not found: Can't resolve './foo.js'` at build.
- 2026-09-01 — This sandbox exports `NODE_ENV=development` globally, which poisons `next build` (React `_global-error` prerender fails with `useContext` of null). The app's `build`/`start` scripts force `NODE_ENV=production` to compensate.
